# 正文速读和总结指南

在第二次阅读和通篇总结使用本文件。

## 第二次阅读的范围

从引言或等效开篇开始，按原文章节顺序推进：

- 有独立实验、评测或实证结果章节：停在该章之前；在它之前独立的训练或实现章节仍包含在速读范围内。
- 无独立实验、评测或实证结果章节：停在结论或等效总结章节之前；穿插的评测内容按原文章节一起速读，不提前截断。
- 两者皆无：按照结构适配规则说明范围。

依据章节功能识别独立的边界章节。方法中举例或提到 experiments，不代表实验章节已开始；Results 可能是理论结果，需要看实际内容。没有独立实证评测章时，沿原文结构读到结论之前，不以首次评测段落作为停止点。

在开头列出本次覆盖的章节和排除的边界章节。用户明确修改范围时跟随用户要求。

## 每章速读的统一框架

按原文题名和编号，用中文标题并附英文原名。每个主要章节通常用 2–4 段，复杂章节按重要小节展开：

1. **本章的问题**：作者为什么安排这一章？它与上一章有什么关系？
2. **关键内容**：主要论证、模块、机制或定理，保留必要条件。
3. **必要解释**：读懂它所需的术语、数据流、公式直觉和符号，按需加入简短例子。
4. **速读结论**：读完应掌握的要点及下一章如何接上。

用上述框架组织信息即可，无须每章机械重复所有标签。

## 按章节功能阅读

- **Introduction**：梳理背景、困难、研究缺口和本文声称的贡献。
- **Background / Related Work**：找与当前工作直接相关的先行方法，说明继承和区别；不要把作者对前人的评价当成已核实事实。
- **Method / Architecture / Algorithm**：先建立整体结构，再拆模块，解释每个模块的输入、处理、输出和核心创新；按需介绍训练阶段、损失、推理过程或算法条件。
- **Analysis / Theory**：明确问题、假设、结论、证明或证据思路；必要时解释界的含义，避免把速读自动升级为全证明推导。
- **Training / Implementation / System Design**：独立实验章之前的这些章节按原顺序阅读，解释设置、流程和资源条件。没有独立实验章时，保留结论之前的完整章节，即使其中穿插实证评测。

对已在 Part 2 讲过的图表，引用编号并补充当前上下文，无须重新完整详解。

## 一次输出完成

把本次范围内所有章节放在同一个回答。可以逐章组织，但不要每章结束后等待用户，也不要自动跨入实验章。

末尾简短连接本轮的论证链，询问是否进入通篇总结；用户提出本章追问时留在本阶段处理。

## 通篇总结

先复查完整论文，包括实际实验或证明、消融、限制及作者结论，再用研究者视角评价。

| 评价面向 | 应回答什么 | 证据要求 |
|---|---|---|
| 主要贡献 | 核心新增内容是什么？通常提炼 1–2 点 | 指明方法或结果的位置，避免把所有已有组件都称为创新 |
| 技术优点 | 哪些设计有价值？为什么？ | 连接机制、对照、分析或证明 |
| 潜在不足 | 已知限制、缺少验证及可能的问题有哪些？ | 区分原文承认、证据显示、尚待检验 |
| 相关工作定位 | 与前人继承、区别或竞争的关系是什么？ | 依据论文或核实的相关一手工作 |
| 启发与延伸 | 可以继续研究什么？为什么值得验证？ | 给合理动机，不把设想写成已取得结果 |
| 适合谁读 | 需要什么背景？适合什么阅读或实践目标？ | 结合论文实际技术门槛和任务 |

用一条清晰的“问题→方法→证据→适用边界”链贯穿总结。批评保持具体、可核验；没有某类实验不等于已经证明方法无效。

只有用户需要时，才扩展详细复现计划、代码实现、数学推导或额外阅读任务。通篇总结完成后，按 SKILL.md 的收尾任务自动生成精简阅读笔记，一并交付并标记本轮完成。
